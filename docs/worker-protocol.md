# Structured worker protocol

`/worker/v1` shares the application TLS listener and uses its own required
`Mitos-Worker-Version: 1` header. Application tokens cannot authenticate workers,
and worker tokens cannot read the application API. Operator-issued opaque worker
credentials are hashed, restricted to pools and agent IDs, expire, can be revoked,
and are fenced by restore epochs.

Issue a credential through the loopback operator listener:

```sh
mitos worker credential --id batch-one --pools interactive --agents mitos.generalist
```

Save the returned token privately as `MITOS_WORKER_TOKEN`. Start a worker on its
own machine with bubblewrap, Codex, and a dedicated `OPENAI_API_KEY`:

```sh
mitos worker --url https://authority.example:8443 --id batch-one \
  --data /var/lib/mitos-worker --ca-file authority-ca.pem
```

Use `mitos worker revoke --id batch-one` to revoke its credential. Set
`MITOS_LOCAL_STRUCTURED_WORKERS=off` on the authority to serve only remote
structured workers. Workspaces, PTYs, and graphs still execute locally. A
registered compatible remote worker allows admission without a native runtime
installed on the authority.

All operations are POST requests: `register`, `claim`, `context`, `progress`,
`renew`, `checkpoint`, `result`, and `release`. Claim supports `?wait=0..20`
seconds. Registration states a fresh incarnation and supported agent IDs. A
successful claim commits pool admission and its Task, Run, incarnation, Task
clock generation, epoch, input/definition/schema digests, acceptance policy and
budget together. Workers receive lease/budget durations; deadlines are server
state. Every mutation supplies the whole binding and a stable `request_id`.
Uncertain HTTP replies are retried with the exact original bytes. Reusing a
request ID with changed bytes conflicts.

Leases last 30 seconds and the worker renews every 10 seconds. Expiry, replacement,
revocation and cancellation fence context reads and mutations. The server creates
a bounded replacement attempt on the same Task after a lost or released grant.
The shared local and HTTP execution library uses the same admission, context and
result handlers. Workspace execution continues through its existing scheduler.

Checkpoints require `structured.checkpoint_schema`, use the same strict object
schema subset as results, are capped at 64 KiB, and store Task/Run, generation,
input and definition digests and schema provenance. They contain application
JSON, never native model sessions. Durable input waits use these portable
checkpoints as described below.

Result acceptance rechecks the binding and current application permission. It
commits registered result/artifact metadata, terminal state, a deduplicated
receipt, and an outbox entry in one SQLite transaction. Authority and context
receipts are generated by the server. Stale results belonging to the worker's
actual previous grant are retained as evidence and return `409 stale_binding`.
Restoring a backup invalidates all pre-restore worker credentials.

Native execution gets a fresh scratch directory, home and model credential
store. It does not inherit application/worker/target credentials or operator
conversation/MCP files. Native approval requests are denied. External effects
use the action gateway; the S3 deployment fault matrix is described below.
`remote_workers` and `mqtt_work_claims` are true after this conformance gate.

## Optional MQTT wake hints

Start the authority with `--worker-wake-config mqtt.json` and the worker with
`--wake-config mqtt.json --wake-pool interactive`. The JSON uses the existing
MQTT transport fields (`broker`, `username`, `password_env`, `ca_file`, and
optional client certificate/key). Remote brokers require TLS; plaintext is
restricted to literal loopback addresses. Broker credentials must have matching
publish/subscribe ACLs for the authority's wake namespace.

Admissions and accepted results commit an outbox entry with their canonical
state. A publisher sends QoS 1, non-retained hints and journals acknowledgement
only after the broker accepts publication. A lost reply may duplicate a hint;
an outage leaves pending entries available after restart. Published entries are
removed from the in-memory pending set, while canonical history retains them.

The topic is `mitos/worker/v1/<home>/pool/<pool>` and the entire payload is
`{"pool":"interactive","capability":"mitos.generalist"}`. It contains no tenant,
Task, Run, input or credential. Worker registration supplies the authority home
namespace. Workers use the shared subscription group `mitos-workers`; any valid
hint means only “poll now.” A coalescing channel bounds pending hints. Without
notifications, a jittered scan every 1–2 seconds discovers work. The TLS claim
handler checks identity, capability, pool, fairness and capacity on every poll.

## External action gateway

The loopback operator endpoint `POST /api/action-targets` configures an ID, tenant,
allowed agent IDs, HTTPS `endpoint`, strict `input_schema`/`result_schema`, and an
optional `bearer`. Literal loopback HTTP is available for local integrations.
Credentials are immutable private files under `credentials`, included by backup;
they are absent from journal records, worker context and tools. A target can be
disabled immediately. Admissions request up to 16 `structured.action_targets`;
foreign or disallowed targets are refused.

Workers use `/worker/v1/action` and `/worker/v1/reconcile` with their ordinary
binding and stable request ID. Action data is `{target,key,payload}`; reconcile
data is `{target,key}`. The native library exposes `mitos_action` and
`mitos_reconcile` only for admitted targets. Other native approval requests stay
denied.

The target adapter contract is:

* POST `<endpoint>/operations` with `Idempotency-Key: <operation-id>` and
  `{idempotency_key,payload}`.
* GET `<endpoint>/operations/<operation-id>` queries the same immutable identity.
* HTTP 200 replies bind `idempotency_key` and explicitly report `applied` with a
  schema-valid `result`, or `not_applied`. All errors, missing identities,
  malformed outcomes, pending results and transport failures are uncertain.

The gateway journals the operation ID, original target revision, payload digest,
and a Task/target hold before dispatch. The immutable admission receipt says
`prepared`; the worker then reconciles the original key to obtain its outcome.
Retries of that admission request return the same receipt. A different worker
request for the same application key resolves to the original operation; changed
payloads conflict. An unresolved hold blocks any new key for that Task and target,
and blocks result acceptance. It survives both server restart and replacement
attempts. Reconciliation queries the original endpoint and credential revision;
it never repeats an uncertain POST. Only explicit `applied` or `not_applied`
removes the hold. A restore or worker replacement cannot undo an external effect.


## Deployment conformance

Run the root test:

```sh
go test -race ./internal/application -run '^TestIndependentWorkerFaultMatrix$' -count=1 -timeout=4m
```

It builds the authority, independent application module and separately deployed
worker subprocess. Cases cover the four application admission/publication crash
boundaries, worker death after claim, actual 30-second lease expiry, duplicate
result delivery, authority death after result commit before reply, authority
restart, MQTT hints published without a worker subscriber, and an external
operation whose applied response is lost. The last case invokes the native action
and reconciliation tools against a real HTTP fixture. Every case verifies one
logical Task, one accepted result and one durable domain reply; the external case
observes one POST. Direct protocol tests additionally retain/refuse stale results,
fence context and renewals, test immediate revocation/restore, and preserve a
Task-level ambiguous-action hold through worker replacement.

The injected crashes require both failpoint opt-in variables. A deterministic
native model stand-in follows the actual confined stdio/tool path. This measures
protocol recovery, rather than production model quality or deployment throughput.

## Durable Task inputs and waits

Applications append `POST /api/tasks/<task>/inputs` with `{key,data}`. Inputs are
bounded JSON objects and receive a per-Task sequence and stable receipt; the key
also binds the original writer and payload. `GET` on that path uses `after` and
`limit` to read the bounded log. These cursors are per-Task input sequences; the
application event feed continues to use global journal sequences. Foreign Task
IDs return 404, and read-only principals cannot append.

A worker with `structured.checkpoint_schema` may call `/worker/v1/wait` with its
binding, stable request ID, and data `{cursor,checkpoint}`. The native library
exposes the same operation as `mitos_wait`. The single writer validates and
commits the schema-declared checkpoint, provenance and consumed cursor together.
If input already exists after that cursor, the receipt says `continue` and
returns a bounded input page. The grant remains active. Otherwise the receipt
says `dormant`, the attempt becomes `waiting`, its Task becomes `dormant`, and the
grant closes in the same transaction. The native executor stops and returns to
claiming work; no human decision or model/session snapshot is involved.

An arriving input and its fresh queued attempt commit together. The wake reserves
a new authority generation, retains Task/request identity and the exact agent
body, and never reopens the old grant. Claim admission still checks current pool,
tenant, principal and target policy. Existing task attempt and elapsed-time
budgets include waits; a denied or exhausted wake still saves the input and
returns `wake_withheld`. Pending inputs are reconsidered when current policy and
queue space permit; denied responsibilities do not prevent other wakes. A resumed
context contains only its portable checkpoint
and the next bounded page of its own Task's input log. Context receipts are
prepared by the server and journaled with their prompt digest.

`TestTaskInputRacesWaitRegistrationWithoutLostWake` races both operations.
`TestTaskWaitAndInputWakeCrashAtomicity` kills processes before/after each commit.
`TestIndependentWorkerDurableWait` exercises the actual confined native tool,
releases the worker, restarts the authority while dormant, appends an HTTP input,
and observes one accepted result on a fresh attempt. Conversation consistency, confinement and declared scale are demonstrated by
the final S4 fixture below.

## Conversation keys and context versions

Structured admission accepts `serialization_key` and `consumed_versions`. A key
is scoped to the tenant and held only while an attempt is active. Conflicting
Tasks may queue, but both readiness and atomic claim admission prevent concurrent
holders. Waiting releases the key; a woken attempt queues behind any newer active
holder. Independent tenants may use the same key.

Version registers begin at zero. Applications advance them with
`POST /api/inputs`, for example:

```json
{"key":"preferences-1","versions":[{"name":"preferences","expected":0,"value":1}]}
```

Advances are monotonic compare-and-set operations, scoped to the authenticated
tenant. The input key binds its writer and entire request; a lost reply can be
retried without applying an advance twice. Global version inputs also appear in
the bounded tenant event feed. Admission rejects a newly requested stale snapshot;
replaying an existing admission key still returns its original receipt.

An input to a dormant Task can include fresh data and
`consumed_versions: {"preferences":1}` without advancing the register again.
Task-local advances implicitly bind their data to the new versions. The register,
input and wake are committed together when applicable. A global advance alone
does not relabel an old checkpoint or old input as current: wake stays withheld
until the application provides an explicit current snapshot. Context receipts
identify the declared versions and the bounded input page used by the worker.

Publication compares every consumed version under the writer lock. A superseded
candidate is preserved as evidence, its grant closes, and `409 superseded_context`
refuses publication. The application can submit a new request with current data.
A candidate must also report a consumed input cursor equal to the current Task
log head. An input arriving first therefore refuses the older candidate and
creates a bounded reconsideration attempt; a result committing first makes a
later input fail visibly against the terminal Task. No acknowledged input can be
silently passed over by an accepted result.

An unresolved external operation may get a replacement grant limited to
reconciliation after its context is superseded. It can query the original effect
but cannot dispatch a new one or publish a stale result. Conversation keys release
on these rejected attempts too.

Worker registration advertises optional protocol features. Wait/checkpoint,
input-log, context-version and action Tasks are offered only to compatible
workers. Current local and standalone workers advertise all implemented features;
base structured workers may continue to execute ordinary headless Tasks.

Race tests cover tenant key independence, active/dormant key transfer, version CAS,
old admission receipt replay, superseded evidence/deduplication, explicit snapshot
refresh, unread input refusal and safe reconciliation after supersession. The S4 fixture and scale evidence below demonstrate `conversation_waits`.


## S4 conformance and declared scale

The [independent conversation fixture](../examples/conversationfixture/README.md)
coordinates private negotiations and a personal thread through HTTP only. Its
process tests force answer/wait ordering, restart while dormant, coordinator
replacement and a preference/publication race. Candidate/company canaries cannot
enter the actual personal prompt, its events/artifacts or MQTT hints. The
coordinator decodes and re-encodes the declared negotiation outcome before
personal admission. The worker cannot read the coordinator database outside its
confined mounts. One outcome and reply are saved transactionally by the application.

The [benchmark report](benchmarks/s4-dormant-scale.md) records replay, Go heap,
process RSS, durable claim latency and read bounds for 20 tenants, 2,000 dormant
responsibilities and 8 active worker identities. Dormant population and execution
capacity are reported separately. These conformance results enable
`conversation_waits`; PostgreSQL remains deferred.
