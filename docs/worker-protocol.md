# Structured worker protocol

`/worker/v1` shares the application TLS listener and uses its own required
`Mitos-Worker-Version: 1` header. Application tokens cannot authenticate workers,
and worker tokens cannot read the application API. Operator-issued opaque worker
credentials are hashed, restricted to pools and agent IDs, expire, can be revoked,
and are fenced by restore epochs.

Issue a credential through the loopback operator listener:

```sh
mitos worker credential --id batch-one --pools interactive --agents mitos.generalist
```

Save the returned token privately as `MITOS_WORKER_TOKEN`. Start a worker on its
own machine with bubblewrap, Codex, and a dedicated `OPENAI_API_KEY`:

```sh
mitos worker --url https://authority.example:8443 --id batch-one \
  --data /var/lib/mitos-worker --ca-file authority-ca.pem
```

Use `mitos worker revoke --id batch-one` to revoke its credential. Set
`MITOS_LOCAL_STRUCTURED_WORKERS=off` on the authority to serve only remote
structured workers. Workspaces, PTYs, and graphs still execute locally. A
registered compatible remote worker allows admission without a native runtime
installed on the authority.

All operations are POST requests: `register`, `claim`, `context`, `progress`,
`renew`, `checkpoint`, `result`, and `release`. Claim supports `?wait=0..20`
seconds. Registration states a fresh incarnation and supported agent IDs. A
successful claim commits pool admission and its Task, Run, incarnation, Task
clock generation, epoch, input/definition/schema digests, acceptance policy and
budget together. Workers receive lease/budget durations; deadlines are server
state. Every mutation supplies the whole binding and a stable `request_id`.
Uncertain HTTP replies are retried with the exact original bytes. Reusing a
request ID with changed bytes conflicts.

Leases last 30 seconds and the worker renews every 10 seconds. Expiry, replacement,
revocation and cancellation fence context reads and mutations. The server creates
a bounded replacement attempt on the same Task after a lost or released grant.
The shared local and HTTP execution library uses the same admission, context and
result handlers. Workspace execution continues through its existing scheduler.

Checkpoints require `structured.checkpoint_schema`, use the same strict object
schema subset as results, are capped at 64 KiB, and store Task/Run, generation,
input and definition digests and schema provenance. They contain application
JSON, never native model sessions. Durable input waits are a subsequent slice.

Result acceptance rechecks the binding and current application permission. It
commits registered result/artifact metadata, terminal state, a deduplicated
receipt, and an outbox entry in one SQLite transaction. Authority and context
receipts are generated by the server. Stale results belonging to the worker's
actual previous grant are retained as evidence and return `409 stale_binding`.
Restoring a backup invalidates all pre-restore worker credentials.

Native execution gets a fresh scratch directory, home and model credential
store. It does not inherit application/worker/target credentials or operator
conversation/MCP files. Native approval requests are denied. External effects
will use the action gateway; the full deployment fault matrix is a later S3
slice. `remote_workers` and `mqtt_work_claims` therefore
remain false until that matrix passes.

## Optional MQTT wake hints

Start the authority with `--worker-wake-config mqtt.json` and the worker with
`--wake-config mqtt.json --wake-pool interactive`. The JSON uses the existing
MQTT transport fields (`broker`, `username`, `password_env`, `ca_file`, and
optional client certificate/key). Remote brokers require TLS; plaintext is
restricted to literal loopback addresses. Broker credentials must have matching
publish/subscribe ACLs for the authority's wake namespace.

Admissions and accepted results commit an outbox entry with their canonical
state. A publisher sends QoS 1, non-retained hints and journals acknowledgement
only after the broker accepts publication. A lost reply may duplicate a hint;
an outage leaves pending entries available after restart. Published entries are
removed from the in-memory pending set, while canonical history retains them.

The topic is `mitos/worker/v1/<home>/pool/<pool>` and the entire payload is
`{"pool":"interactive","capability":"mitos.generalist"}`. It contains no tenant,
Task, Run, input or credential. Worker registration supplies the authority home
namespace. Workers use the shared subscription group `mitos-workers`; any valid
hint means only “poll now.” A coalescing channel bounds pending hints. Without
notifications, a jittered scan every 1–2 seconds discovers work. The TLS claim
handler checks identity, capability, pool, fairness and capacity on every poll.

## External action gateway

The loopback operator endpoint `POST /api/action-targets` configures an ID, tenant,
allowed agent IDs, HTTPS `endpoint`, strict `input_schema`/`result_schema`, and an
optional `bearer`. Literal loopback HTTP is available for local integrations.
Credentials are immutable private files under `credentials`, included by backup;
they are absent from journal records, worker context and tools. A target can be
disabled immediately. Admissions request up to 16 `structured.action_targets`;
foreign or disallowed targets are refused.

Workers use `/worker/v1/action` and `/worker/v1/reconcile` with their ordinary
binding and stable request ID. Action data is `{target,key,payload}`; reconcile
data is `{target,key}`. The native library exposes `mitos_action` and
`mitos_reconcile` only for admitted targets. Other native approval requests stay
denied.

The target adapter contract is:

* POST `<endpoint>/operations` with `Idempotency-Key: <operation-id>` and
  `{idempotency_key,payload}`.
* GET `<endpoint>/operations/<operation-id>` queries the same immutable identity.
* HTTP 200 replies bind `idempotency_key` and explicitly report `applied` with a
  schema-valid `result`, or `not_applied`. All errors, missing identities,
  malformed outcomes, pending results and transport failures are uncertain.

The gateway journals the operation ID, original target revision, payload digest,
and a Task/target hold before dispatch. The immutable admission receipt says
`prepared`; the worker then reconciles the original key to obtain its outcome.
Retries of that admission request return the same receipt. A different worker
request for the same application key resolves to the original operation; changed
payloads conflict. An unresolved hold blocks any new key for that Task and target,
and blocks result acceptance. It survives both server restart and replacement
attempts. Reconciliation queries the original endpoint and credential revision;
it never repeats an uncertain POST. Only explicit `applied` or `not_applied`
removes the hold. A restore or worker replacement cannot undo an external effect.
